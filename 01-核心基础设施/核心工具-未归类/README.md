# `核心工具-未归类/` —— 拆收容所之后剩下的那批

2026-09-17 把 `01-核心基础设施/共享小工具-未细化/`（466 个 js + 109 个随行资源）
按主题拆开了，这里是**剩下的 178 个**。逐文件的判定表见
`.analysis/move/hub-plan.json`（`keep` 里 `cluster: null` 的那些）。

## 为什么留在这里

按仓库铁律：**一个看起来合理但错的名字比没有名字更糟**。归类只采硬证据 ——
它 import 了哪个包自己的 chunk、包名/API 名/错误串是否出现在文件里、仓库自己的
文档有没有写明。够不上这三条的就不搬。这批的典型理由：

- **文件内没有任何可读字符串**（导出名仍是混淆名、没有错误串、没有遥测事件名），
  调用点又分散在好几个模块 —— 例：`chunk-7jfz2w01.js`、`chunk-fgegxt0m.js`
- **调用点跨度过大**，没有单一归属 —— 例：`hover-rest-transcript.js`（11 个模块引用）、
  `mcp-control-handlers.js`（跨 6 个模块）
- **两个方向都说得通**，定不下来 —— 例：`version-policy.js`（自动更新 vs 策略限制）、
  `diff-hunks.js`（差异引擎 vs 工具 UI 渲染）

## 怎么用这个目录

按名字找东西**不可靠** —— 这里的文件名有的是语义名、有的是 `chunk-<id>.js`，
而留在这里的理由恰恰是「名字之外没有证据」。要看某个文件是什么，
读它的导出名与调用点（`_index/file-map.json` 里有它的 chunk id 与出处）。

## 一个有用的判据

`chunk-j86cs2ar.js` 是这批里最值得先看的一个：它文件内无可读串，但被 **8 个模块**
引用（Bridge / CLI / Fleet / 会话历史 / 后台任务 / 斜杠 UI / 自动更新 / 自托管 Runner），
这种跨度基本可以确认是共享基础设施 —— 只是确认不了是哪一类。
